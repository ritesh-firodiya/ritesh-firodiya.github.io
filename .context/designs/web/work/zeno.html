zeno

Open source · MIT v0.7.0

A Claude Code plugin and a CLI. It keeps many product repos on the same rules, makes past decisions searchable, and makes Claude weigh a request before it acts on it.

The problem

Rules drift

The same rules were copied into fifteen CLAUDE.md files. Each copy changed on its own.

Decisions get re-made

Every session starts fresh. A choice settled last month came back as a new idea.

The agent says yes too fast

A large request got built before anyone asked if it was worth the cost.

How it works

Plugin

Inside every Claude session

  • weigh the decision gate
  • challenger a second opinion on large asks
  • ask, ingest, decision the wiki
  • a session hook that loads the rules
  • a local search server (QMD)

CLI

In the terminal and in CI

  • zeno init sets a repo up
  • zeno check fails on a broken rule
  • zeno sync moves every repo forward
  • zeno learn turns overrides into proposals
  • zeno ui wikis, designs, import graphs

Config

One file, three layers

Estate, then repo, then local. The closest layer wins. Turning a check off needs a written reason.

kind: expo-app modules: [docs, design, code, architecture] packs: [expo]

What it caught

  • ScrvioA controller reached into the database. The rule says only repositories touch Prisma. zeno check failed until it moved.
  • EstateA move to Firebase that would have cost more. The gate pushed back with the current bills and the four Postgres apps.
  • EstateInstructions for tools no longer in use. Old .cursorrules and Copilot files flagged, so the agent reads one source.

Decisions worth defending

  • A verdict with no citation is an opinion. Every reason names a principle and a file. That makes a verdict checkable, and wrong ones easy to spot.
  • Push back stops work, but you can override it. The override and its reason are logged. zeno learn reads the log and proposes rule changes.
  • Each repo owns its architecture. Import rules live in the repo as dependency-cruiser config. A tested tool, not a custom linter.
  • Measured, not assumed. Five eval cases run with and without the plugin on a sample product.

The principles a request is weighed against

  1. C-01 Shipping beats starting
  2. C-02 One home per fact
  3. C-03 Knowledge is written down, in the repo
  4. C-04 Decided things stay decided
  5. C-05 Value must beat cost
  6. C-06 Write less
  7. C-07 Tested tools over custom ones
  8. C-08 Products evolve together
  9. C-09 Hard rules are code
  10. C-10 Secrets are never lost and never leaked
  11. C-11 Verified, one step at a time
  12. C-12 Reversible before irreversible
  13. C-13 Users' money and data are handled exactly
